PURPOSE

Provide a menu-driven Windows BAT workflow for explicitly selected source
color, including linear Rec.709 ProRes 4444, optional subject mattes, output
formats and color, and GPU/cache/output settings. Package the local installation
with a relocatable Python runtime so a complete installed-folder copy can run
on another compatible Windows x64 NVIDIA PC.

BAT ENTRY POINT

- Adds setlocal so PATH/Python environment changes stay inside this invocation.
- Sets the working directory from the BAT's own location, supporting folder
  names with spaces and launching from a different working directory.
- Adds the application folder and optional venv Scripts folder to process PATH
  so the bundled ffmpeg.exe is available to child processes.
- Sets PYTHONUTF8=1 and PYTHONUNBUFFERED=1 for paths/logging and timely progress.
- Prefers runtime/python.exe from the portable payload.
- Falls back to venv/Scripts/python.exe for conventional source installations.
- Reports a missing interpreter instead of silently using an unrelated system
  Python with missing dependencies or an incompatible version.
- Invokes corridorkey_launcher.py and forwards dropped arguments with %*.
- Retains the final pause so errors/results stay visible.
- Captures the launcher's exit code before pause and returns that code.

NEW GUIDED LAUNCHER

corridorkey_launcher.py reuses the upstream terminal prompt and companion-mask
helpers from run_interactive.py. It adds typed Settings, Job and PreparedMedia
records and handles selection, preparation and subprocess execution. It does
not modify the model architecture, inference math or downloaded checkpoints.

Input selection:
- Accepts a dropped video, a frame folder, a folder with an Input subfolder,
  a batch folder, or multiple explicit dropped inputs.
- Video extensions: MOV, MP4, MKV, AVI, WEBM and MXF.
- Frame extensions: EXR, PNG, JPG and JPEG.
- Deduplicates repeated input paths.
- Distinguishes a batch folder containing source videos and companion matte
  PNGs from an actual frame sequence. A companion image is not processed as the
  source in place of the video.
- Excludes conventional _AlphaHint videos from implicit batch source lists.

Input color and levels:
- Menu choice 1: sRGB.
- Menu choice 2: Rec.709 using the inverse BT.709 opto-electronic transfer.
- Menu choice 3: Linear Rec.709, gamma 1.0, including linear ProRes 4444.
- Offers Auto, Limited/video/TV and Full/data/PC video-range choices.
- Explicit input color overrides ambiguous video transfer metadata. ProRes
  4444 is a codec/container choice, not proof of a particular transfer function.
- The Rec.709 option is inverse BT.709, not a generic gamma-2.4/BT.1886 mode.

High-precision video preparation:
- Uses OpenCV only to probe source FPS/count; it does not use OpenCV's 8-bit
  video-frame reader to feed the model in this launcher.
- FFmpeg decodes the first video stream through a BT.709 YUV-to-RGB matrix
  into planar float RGB and compressed float EXR frames.
- The zscale transfer is held linear on both sides during this matrix/range
  decode, deliberately avoiding a zimg display-EOTF interpretation of BT.709.
- Explicit source transfer equations are then applied once to the float RGB
  for sRGB or Rec.709. Linear Rec.709 gets no additional transfer conversion.
- Uses signed sRGB and BT.709 transfer equations for finite negative values.
- The same equations are used for source frame sequences, ensuring consistency
  between video and sequence inputs.
- Preserves native frame dimensions, ordering and probed fractional FPS.
- Frame limits decode only the selected leading N frames; all is the default.
- Discards source audio/subtitles/data for inference; original audio remains
  the editor's responsibility.
- Passes prepared frames via --frame_dir_linear and --frame_dir_fps into the
  existing infer.py frame-directory path, so the runtime does not gamma-decode
  already-linear values a second time.
- Integer frame sources are normalized from their native dtype. Linear EXR
  sequences can use the source frames directly without a redundant conversion.

Matte selection:
- No matte: ignores companion masks and leaves subject selection to the model.
- First-frame matte: accepts an existing image or frame directory.
- Full matte: accepts an existing grayscale coverage video or frame directory.
- Uses white for subject coverage and black for background; image alpha can
  supply first-frame coverage through the upstream hint loader.
- Offers explicit matte trust, with 0.95 default for a clean mask and 0.75
  described as appropriate for a rough automated mask.
- Full matte mode offers authoritative per-frame hints, routed to
  --no_carry_hint. Otherwise the existing carried-prediction defaults apply.
- Discovers first-frame companions such as shotFrameHint.png and full-video
  companions such as shot_AlphaHint.mov/mp4, then asks before using them.
- A still-image companion is not silently accepted as a full matte video.
- Supports an AlphaHint companion folder for structured frame inputs.
- Missing or unsupported explicit matte paths are reprompted. The launcher
  does not silently fall back to no-matte inference.
- Full matte videos are decoded to float grayscale EXR coverage without a
  gamma transform. Checks video FPS against source FPS and checks that enough
  mask frames exist for the selected segment.
- An existing alpha channel in the SOURCE VIDEO is not automatically treated
  as a matte. The three selections describe separately supplied guidance.

Export choices:
- Video: ProRes 4444 transparent cutout plus selected H.264 alpha/foreground/
  checker previews, using the existing runtime writers.
- EXR: linear HDR image sequences, with half or full float selection.
- Select any combination of alpha, fg, cutout and checker; defaults to all.
- Validates numbered output selections instead of silently replacing invalid
  input with all outputs.
- Video cutout has an independent straight-sRGB or straight-linear-Rec.709
  output-color choice, forwarded as --cutout_linear when appropriate.
- EXR remains scene-linear; its cutout includes RGBA.
- Exposes despill strength in [0,1], default 0.5.
- Runtime video clipping to [0,1] and preview sRGB encoding remain upstream
  behavior. EXR is the float/HDR export path.

Resources, execution and records:
- Auto GPU-memory selection remains the default; manual mode exposes the
  existing low-VRAM and Hann chunk/stride choices.
- Offers leading-frame limit, output parent folder and temporary-cache folder.
- Prints source color, levels, matte mode, output choices, cutout color, frame
  limit, cache location and every source/destination before confirmation.
- Rejects collisions when multiple sources map to the same output directory.
- Calls out existing nonempty output folders before Start confirmation.
- Uses a generated per-job temporary directory. Decoded frames and low-VRAM
  feature files share that job lifetime and are removed on success/failure/
  cancellation. Temporary disk needs can be substantial for long 4K shots.
- Model subprocess uses sys.executable, keeping the bundled interpreter in
  portable mode. Forces local/offline Hugging Face model loading.
- Waits for the model subprocess before deleting temporary frames. On Ctrl+C,
  terminates/waits for the child and escalates to kill only after a timeout.
- Saves launcher_settings.json with original source/matte paths, selected
  settings, FPS and the executed inference command in each output folder.
- Nonzero inference exit codes are reported as errors, not successful jobs.

PORTABLE RUNTIME BUILD

tools/make_portable.ps1:
- Locates the installed venv and resolves its matching CPython base runtime.
- Accepts explicit -SourceEnvironment and -PythonHome for another build source.
- Accepts -VCRedistDirectory for an explicit Microsoft x64 app-local CRT source,
  otherwise discovers the SDK's Microsoft.VC*.CRT directory in standard Visual
  Studio / Build Tools installation paths.
- Requires a matching Windows CPython 3.11 runtime with python311.dll.
- Copies the base Python executable, DLLs, standard library and bundled MSVC
  runtime DLLs, plus all installed site-packages into runtime/.
- Adds runtime/python311._pth with ONLY relative search paths: runtime root,
  Lib, DLLs, Lib/site-packages and the application root, then import site.
- The _pth file enables isolated mode, avoiding user-specific registry paths,
  external PYTHONHOME/PYTHONPATH and unrelated user site packages.
- Removes copied virtualenv-only startup hook files from the new runtime.
- Copies all app-local DLLs from Microsoft.VC143.CRT into the Python executable
  directory. The local build uses Visual Studio Build Tools CRT 14.44.35112,
  including MSVCP140, its helper DLLs, VCRUNTIME140, VCRUNTIME140_1,
  VCRUNTIME140_threads, CONCRT140 and VCCORLIB140.
- Checks imports for PyTorch/OpenCV/Transformers/utils3d and asserts that every
  Python search path resolves inside the application folder.
- Uses Windows GetModuleFileNameW to verify that required MSVCP140 and
  VCRUNTIME140 DLLs actually load from this payload. This closes the gap where
  a same-machine folder-copy test could silently use an installed system VC++
  runtime and fail later on a clean target PC.
- Refuses to overwrite an existing runtime directory.

Portable payload:
- runtime/ contains Python 3.11.15 and all installed dependencies.
- PyTorch 2.9.1+cu128 and torchvision 0.24.1+cu128 include their CUDA 12.8 runtime
  components. A separate CUDA toolkit installation is unnecessary.
- ffmpeg.exe is local to the application folder.
- weights/ and vfms/ contain all downloaded model assets.
- Application code, third_party/, runtime, weights, vfms and FFmpeg must remain
  together. Folder renaming and changing the parent directory are supported.
- The target PC still needs compatible Windows x64 hardware and an NVIDIA
  GPU driver. This payload is not a Linux/macOS build and cannot supply a GPU
  driver. Portability does not make an unsupported GPU supported.

VALIDATION AND REGRESSIONS

tests/test_launcher.py uses unittest and actual FFmpeg/ProRes decoding where
precision matters. Its 10 tests cover:
1. Linear ProRes shallow-ramp round trip: preserved midtones, native 128x64,
   leading-frame limit, fractional 24000/1001 FPS, >90 distinct decoded ramp
   levels and maximum allowed sample error 0.004.
2. Explicit sRGB, BT.709 and identity-linear transfer equations.
3. Real ProRes Rec.709 midgray decode, expected ~0.2595894 for encoded 0.5,
   allowing 0.004 codec quantization error. Catches the erroneous darker zimg
   display-EOTF interpretation (~0.191 in the initial implementation).
4. Terminal selections route linear input, first-frame matte and linear cutout.
5. Accepting menu defaults maps all frames to the -1 sentinel, avoiding an
   attempted int('all') conversion.
6. No-matte mode ignores discovered companions; missing full masks reprompt.
7. Full-matte command includes explicit matte frames, authoritative mode,
   linear input and EXR/FPS routing.
8. Recognizes both flat frame folders and Input-subfolder structures.
9. A video batch with shotFrameHint.png processes the actual video source.
10. Full-matte mode rejects an image-only first-frame companion.

before running a long shot. Use upstream color conversion for unsupported
source gamuts/transfers; choose EXR when unclipped HDR output is needed.

BUGFIX FOLLOW-UP - 2026-10-21 - FRESH MP4 STARTUP / OPENEXR

User-visible failure:
The BAT could decode a source MP4 to temporary EXRs, then abort while opening
the EXRs with OpenCV: (-213) OpenEXR codec is disabled. This affected non-linear
source choices (sRGB and Rec.709) in a fresh launcher process. MP4 and the
supplied matte were supported; this was a launcher initialization-order bug.

Root cause:
video_metadata() imported cv2 before decode_video() attempted to set
OPENCV_IO_ENABLE_OPENEXR. OpenCV had already cached its codec configuration.
The late environment assignment could not enable the codec for that process.
Initial source tests enabled EXR globally for their fixtures, masking this
failure. The original actual BAT integration cases selected linear ProRes,
which did not read/rewrite temporary EXRs in the parent before model startup.

Source changes in this follow-up:
- corridorkey_launcher.py: enables OPENCV_IO_ENABLE_OPENEXR=1 at module startup,
  before importing project helpers or OpenCV. Removes the misleading late
  assignments inside decode_video() and decode_sequence(). This also covers
  direct corridorkey_launcher.py use without the BAT.
- CorridorKey_DRAG_CLIPS_HERE.bat: sets OPENCV_IO_ENABLE_OPENEXR=1 before Python
  starts. setlocal keeps that environment change scoped to this invocation.
- The required flag is explicitly enabled even if an inherited environment
  value is 0, because this launcher's internal float-EXR pipeline requires it.
- tests/test_launcher.py: adds a real MP4 regression that spawns NEW Python
  processes for each source-color choice (sRGB and Rec.709), testing both an
  unset flag and an inherited value of 0. Each process probes video metadata,
  decodes two MP4 frames, and reads the float EXRs at the correct dimensions.
  No test-process cv2 import or global flag can hide the startup-order failure.
- changelog.txt: records this bug, its cause, exact patch and validation.

Verification:
- Reproduced the user's exact OpenCV failure in all four fresh-process cases
  before the fix. All four cases pass after the fix.
- Full source suite: 11 tests pass with bundled runtime/python.exe.
- Actual BAT MP4-source + full-MP4-matte GPU inference passed in a new process
  with the inherited EXR flag unset: exit 0, four decoded 640x360 output frames,
  transparent ProRes alpha plane verified, and temporary job cache cleaned.
  Retained local log/report: out_mp4_exr_fix/ (ignored by Git).

No new dependency, runtime rebuild, checkpoint download or codec change is
required. The installed portable folder uses the patched source immediately.
An earlier copy on another PC needs the updated BAT and launcher Python file;
copy the updated tests/changelog as well when synchronizing development files.
